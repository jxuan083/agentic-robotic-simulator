# 實驗室環境一鍵入口、聊天視窗與相機畫面

一個指令就能開好整套實驗室環境：模型服務、模擬伺服器（含常駐相機畫面）和聊天視窗。用聊天視窗下單後，模擬手臂完成任務，可以從頭走一次競賽流程。場景與相機見 [lab-scene-cameras.md](lab-scene-cameras.md)，聊天規則見 [chat-layer.md](chat-layer.md)。

## 使用

```bash
uv run tools/lab.py                                       # MuJoCo、Q4 模型、lab_20261120、預設積木
uv run tools/lab.py --backend isaac --model bf16 --block-colors red,blue,blue,yellow
uv run tools/lab.py --wrist-lens pinhole                  # 腕部畫面用理想針孔
uv run tools/lab.py --no-chat                             # 只開模擬器
```

`tools/lab.py` 依序啟動下列元件，每一步都等前一步回應才繼續；任一步失敗就停下並說明原因：

1. **模型服務**：
   - Q4_K_M：llama.cpp，`docker/llamacpp/serve.sh`，port 8001，預設。
   - BF16：vLLM，`docker/vllm/serve.sh`，port 8000。
   - 已經在執行就直接沿用。
2. **模擬伺服器**：`tools/mujoco_server.sh` 或 `docker/isaac/server.sh`，再依參數載入 experiment（預設 `lab_20261120`）。已經在執行就沿用，並用這次的參數重新載入。
3. **聊天視窗**：`tools/chat_window.py`。

- **重開聊天視窗**：關掉聊天視窗不會結束環境，模擬器、模型和進行中的任務都繼續跑。有兩種方式重開：
  - 在入口的終端機按 Enter。
  - 自己執行 `uv run tools/chat_window.py --backend <引擎>`。

  重開的視窗會先顯示目前待回答的問題，然後接著同一個任務。
- **結束整套環境**：在入口按 Ctrl+C，或關掉模擬器視窗。
- **只清理自己建立的服務**：
  - 各服務的控制腳本在 `up` 時，只有在服務不存在時才建立，並把建立出來的實例身分寫給入口：
    - 模型服務：用容器名稱判斷，容器 ID 由 docker 的 `--cidfile` 寫出。兩邊同時建立時，搶輸的一方視為沿用。
    - Isaac 伺服器：在鎖內檢查並建立，寫出容器 ID。已在執行的伺服器不會被重建。
    - MuJoCo 伺服器：在鎖內檢查並啟動，寫出程序 PID。
  - 入口結束時只關自己建立的那個實例（`down <容器 ID／PID>`）。即使啟動或就緒逾時（`--start-timeout`），也會被清掉，下一次可以直接啟動。如果同名服務已換成別人的實例，入口不會動它。
  - 已存在的服務（包括還在暖機的，或另一個入口剛好先建立的）一律沿用，結束時不關。
  - 容器名稱、port、模型名稱由腳本的 `info` 提供，所以 `LLM_CONTAINER_NAME`、`LLM_PORT`、`LLM_MODEL` 在查詢、啟動、清理三處都一致。
  - 任一元件失敗時，入口會說出是哪個元件，並回傳 1。

`tools/sim.py`（選單、驗收）與 `tools/chat.py`（命令列、對話腳本）照舊可用。

## 聊天視窗

- 是獨立的 Tk 小視窗，和模擬器在不同程式中。可以單獨關掉、重開，不影響模擬器。
- 視窗內容：
  - 狀態列：模擬器、模型、暖機時間、連線狀態。
  - 待回答的問題列：黃色。
  - 對話紀錄。
  - 輸入框：按 Enter 送出。
- 規則和命令列聊天相同，沿用同一個 `ChatAgent`：
  - 回答綁定的是視窗「實際顯示」的問題：輸入框從空白變成有內容時，記下當時畫面上的題號。打字、輸入法上字、貼上都算。
  - 背景剛收到、還沒畫出來的新題，不算使用者看過。
  - 清空重打時重新綁定。送出時把綁定的題號交給既有的題號檢查。
  - 追問綁定發問的題號。
  - 重開視窗時，先顯示目前待回答的問題。
- 單獨開：先開模擬器和模型服務，再執行 `uv run tools/chat_window.py --backend mujoco`。

## 相機畫面（常駐）

- 場景有感測相機時，D455 global 與腕部畫面固定在主畫面內，不接受操作：

| 引擎 | 位置 |
|---|---|
| MuJoCo | 3D 視圖右上角 |
| Isaac | 停靠在 3D 視窗下方，左邊 global、右邊腕部，沒有關閉鈕 |

- Isaac 的相機視窗只建立一次。Reset、換積木數量、伺服器重建 session 時，只把視窗改指到新 session 的相機；換到沒有相機的場景時先隱藏。

## 腕部畫面的鏡頭變形

腕部相機實機有桶形變形。模擬預設 `real` 模式，讓腕部畫面看起來像實機原始影像；`pinhole` 模式是理想針孔。

- **切換方式**：
  - `tools/lab.py --wrist-lens`
  - 兩個 teleop 腳本的 `--wrist_lens`
  - experiment 選項 `wrist_lens`
  - 預設值：場景檔的 `sensor_cameras.wrist.lens_mode`
- **鏡頭模型**：OpenCV 徑向模型，640×480，fx = fy = 400、cx = 320、cy = 240、k1 = −0.15，其餘係數 0（`estimated`）；安裝位姿仍是 `provisional`。下表都是用這組數值本身量的：

  | 證據 | 原圖／理想針孔 | 本組參數 | 公開 U20CAM 參數（f 550、k1 −0.448、k2 0.215） |
  |---|---|---|---|
  | 直邊殘差：38 張實拍、83 段邊緣，越小越直 | 6.82 | **4.25** | 4.17 |
  | 夾爪重疊率：7 幀同關節姿態，越高越吻合 | 0.72（理想針孔） | **0.73** | 0.33 |

  - 公開參數讓直邊變直的程度相當，但模擬夾爪偏小偏下，只留作參考。
  - 之後要用棋盤格校正我們自己的相機來取代。
- **MuJoCo 的做法**：先在畫面外算一張較寬的針孔畫面（960×720，垂直 85.7°），再逐像素重新取樣成 640×480。實作在 `src/agentic_sim/wrist_lens.py`。
- **Isaac 的做法**：腕部相機套用 RTX 的 OpenCV pinhole 鏡頭模型（`OmniLensDistortionOpenCvPinholeAPI`），係數相同。
- **兩個引擎一致**：用格線測試比對，相差不到 1 px。

### 把實拍拉直（離線）

```bash
uv run tools/undistort_wrist.py <原始腕部影像.png> [...] [--out-dir DIR]
```

- 用途：從實拍這一側對照，把原始腕部影像拉直。模擬器不必開。
- 依賴：只要 numpy、PyYAML，以及 PATH 上的 ffmpeg／ffprobe。不需要 MuJoCo、OpenGL 或 OpenCV，`MUJOCO_GL` 不必設定。影像讀寫在 `src/agentic_sim/image_io.py`，鏡頭參數直接讀場景檔，和模擬用的是同一組。
  - 沒有 uv 的環境可以直接用：`python tools/undistort_wrist.py ...`。
- 輸入：必須是原始 640×480 腕部影像。
- 輸出：`<檔名>_flat.png`，放在原圖旁邊或 `--out-dir`。
- 寫檔前先檢查整批。有下列任一情況就列出原因、一張都不寫，並回傳 1：
  - 尺寸不是 640×480（裁切或縮放過的）。
  - 讀不到影像。
  - 某張的輸出正是另一張輸入，例如同時給 `frame.png` 和 `frame_flat.png`。
  - 兩張的輸出同名，例如 `a/frame.png` 和 `b/frame.png` 指定同一個 `--out-dir`。
- 原圖一律不會被寫入。
- 拉直方式：
  - 輸出沿用原始內參（fx 400、中心 320／240），所以畫面中央的比例不變。
  - 拉直後超出 640×480 的外圍會被裁掉；桶形變形的反向不會產生黑邊。
  - 取樣用雙線性內插。
- 驗證：
  - 同一批 83 段邊緣，拉直前後的彎曲度從 6.82 降到 4.25。
  - 這些邊緣依鏡頭模型換算後的位置，95% 落在拉直影像的邊緣上（1.5 px 以內）。
  - 範例幀的盤緣從 5.99 降到 2.07。

## 實驗室場景的起始姿態

- 手臂從實驗室的收折休息姿態開始，即場景 `robot.start_pose_lerobot`（實機讀值），再以 0.8 rad/s 移到操作起點，約 1.3 秒。
- 夾取方向沿用切線方向（`robot.grasp_heading_deg: 90`），所以 home 時腕部旋轉約 93°。
- 實驗室操作者習慣把手腕放在 0° 左右，但模擬中這個方向在需要傾斜夾爪的遠處積木會滑落：兩指在傾斜平面內，一高一低。
- 積木角度不固定時，執行器會在每 90° 對稱的方向中挑最近的一個，手腕最多轉 ±45°。

## 驗收

- **競賽流程**（兩個引擎都用 `tools/lab.py` 一鍵啟動，用 Q4 模型）：
  1. 積木為一紅兩藍一黃，在聊天視窗打「我要兩顆紅色、一顆藍色」。
  2. 交付一紅、一藍後，跳出缺料問題。
  3. 在聊天視窗回答「換成黃色」。
  4. 交付黃色，帳本完成（一紅一藍一黃）。

  | 引擎 | 從下單到完成 |
  |---|---|
  | MuJoCo | 約 32 秒 |
  | Isaac | 約 56 秒 |

  - 這次的輸入由聊天視窗的 `--type` 依序打進輸入框，和手動打字走同一條路徑。
  - 關掉聊天視窗後，入口關掉它開的模擬伺服器和模型服務。
- **實驗室場景的任務情境**（MuJoCo，開發檢查）：缺料換色 8/8、持物交付 10/10、下降中改單 9/9。
- **Isaac 伺服器連續重建 3 次**（實驗室 → 最小場景 → 實驗室）：相機畫面保留在原位，並顯示新場景。
- **PR #12 審查後的修正與驗收**：
  - 回答綁定：新增 6 項測試，在視窗層手動控制「背景收到」和「畫面顯示」的先後，鍵盤與貼上各跑一次。
    - 畫面顯示 A、背景已收到 B 時開始輸入，該句不回答 B；B 維持待答，帳本不變。
    - 尚無題目時先輸入，該句也不回答之後出現的 B。
    - 清空重打後，只回答一次。
  - 重開聊天視窗（兩個引擎）：
    - 在缺料詢問時關窗，入口、模擬器與模型都繼續跑。
    - 重開後 session、題號、revision、已交付數量都和關窗前一致，視窗先顯示原題。
    - 回答「換成黃色」後，黃色只交付一次，最終一紅一藍一黃；按 Ctrl+C 清理入口自己啟動的元件。
  - 服務歸屬（實際服務）：
    - Q4 容器已存在、尚未就緒：沿用，結束後仍在。
    - 新建的 Q4 就緒逾時：回報元件並回傳 1，下一次可以直接啟動。（當時逾時設 5 秒，腳本還在檢查模型檔，實際尚未建立容器；容器已建立後逾時的情況見第二輪。）
    - Q4 原已就緒：結束後模型仍在、模擬器已關。
    - Isaac 伺服器就緒逾時：容器已移除。
- **PR #12 第二輪審查後的修正與驗收**：
  - 服務歸屬改成記錄實際建立的實例（實際服務，Q4 與 Isaac）：
    - 兩個入口交錯：A 查不到 Q4、停在建立之前，B 建立並就緒後再讓 A 繼續。A 沿用 B 的容器；A 結束後容器 ID 不變且可回應，B 結束後才關閉。
    - 自訂名稱 `LLM_CONTAINER_NAME=team-q4` 暖機中啟動入口：沿用，結束後容器 ID 不變並可回應。等待逾時（1 秒）時也一樣保留。
    - 新建的 Q4（逾時 25 秒，模型檔檢查約 23 秒後建立容器）與 Isaac（逾時 10 秒）在就緒前逾時：回報元件，清掉本次建立的容器，下一次直接啟動成功。
    - MuJoCo：事先啟動的伺服器被沿用、結束後仍在；`down` 帶別的 PID 不會關它；入口自己啟動的，按 Ctrl+C 後已關閉。
  - 批次拉直：輸出撞到另一張輸入（兩種順序）、兩張輸出同名都在寫檔前拒絕，結束碼 1，原圖雜湊不變，沒有任何輸出；正常批次每張各產生一張 640×480。
  - 離線拉直：在只裝 NumPy、PyYAML 的獨立環境（沒有 MuJoCo，`MUJOCO_GL` 未設定）執行：
    - `--help` 正常。
    - 實拍拉直結果和前一版逐像素相同。
    - 320×240 被拒絕，結束碼 1。
- **測試**：151 項全過。

  - Isaac：smoke 2/2、keyboard_pick_place 8/8、mouse_pick_place 10/10。

## 限制

- 鏡頭參數是由實拍推算的，還沒有用棋盤格校正。腕部相機的安裝位姿沿用官方相機座模型。
- 驗收用的是自動輸入。實際使用時，模型對新句型的判斷仍以 [chat-layer.md](chat-layer.md) 的語句表結果為準。
- 聊天視窗只送任務命令；要讓手臂停下，用模擬器的 Pause（P）。
